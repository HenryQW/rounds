# Delegation safety feasibility check

This check records evidence for the planned Rounds Router Workspace. It does not establish a production approval or isolation boundary.

## Results

| Area | Evidence | Result |
| --- | --- | --- |
| Delegate environment | Installed `billion-context` 0.1.216, `dist/agent/pi-native.js:1161` | `delegateChildEnv` copies `process.env` to the child. Credentials in that environment can reach it. |
| Explicit cancellation | A disposable `acp_delegate` worker started a shell and `sleep 45`. After the worker and child processes were observed, `acp_delegate_cancel` was called. | The worker, shell, and sleep process were absent in the subsequent `ps` checks. This covers one shell child, not a complete agent tree. |
| Bouncer exit | An isolated Pi session used `billion-context` 0.1.216 and a local scripted model to launch a Bartender and Barback. The Bouncer exited once by standard-input closure and once by `SIGKILL`. | In both runs the Bartender, Barback, and Barback's shell were still running after the Bouncer exited. Test-owned processes were stopped afterward. |
| Process-group cleanup | The same isolated tree ran in a dedicated process group. After Bouncer exit, a test supervisor sent `SIGTERM` to that group. A Barback also started a test process in a new session with `setsid`. | The normal Pi agents and shell exited, but the detached test process survived. It was then identified and stopped separately. Process-group cleanup alone is insufficient. |
| Sandbox inheritance | A test-only `sandbox-exec` profile wrapped the real three-level Pi tree. It denied one dummy secret file and one local test port, and permitted the local scripted model port. The Barback attempted both restricted operations. | Both attempts returned `PermissionError`; all three agents reached the scripted model. The profile allowed other operations by default. It does not establish a complete security boundary or action-bound approval. |
| Container termination | A disposable, labeled container used the existing local Docker engine with no network, no host mounts, a read-only root and dropped capabilities. A test supervisor verified its label, mounts and command, then killed and removed it. Docker reported the container stopped. Automatic crash cleanup and approval enforcement remain unverified. |
| Pi inside a container | A network-isolated `node:24` container used a read-only copy of Pi 1.5.2 and `billion-context` 0.1.216, a disposable writable directory, and a scripted model on the container's loopback. The Bouncer called `acp_delegate`, the Bartender called `acp_delegate`, and the Barback used Bash. | All three Pi sessions started at depths 0, 1, and 2. The Barback created a test marker. | Watchdog heartbeat | A network-isolated container ran the actual Pi agent tree as an unprivileged user under a root-owned watchdog. The watchdog used elapsed monotonic time to detect stale values. | The watchdog observed the stale heartbeat and the container stopped. This tests one crash signal and a detached child. | Host model transport | A network-isolated container ran the actual Pi agent tree. A guest loopback adapter used `docker exec -i` standard input and output to reach a host-side scripted model. Closing input stopped the adapter and the loopback connection failed. This tests buffered synthetic exchanges and one idle disconnect, not real Magpie access. Streaming, in-flight disconnects, host request validation, resource limits, organization rules, and protected-action approvals remain unverified. |
| Effective model protocols | A read-only Pi extension queried the effective Magpie model registry without printing credentials. Three sample model IDs reported `openai-responses`, `anthropic-messages`, and `openai-completions`. | Resolve the selected model and protocol at launch. A relay cannot assume one API for every model. This does not test real model calls, authentication injection or organization authorization. |
| Disposable checkout | A network-isolated container received a disposable `git clone --no-local` with its Git metadata mounted read-only. Dirty checkout handling, safe diff inspection, approved integration and concurrent worktrees remain unverified. |
| Pi stream parsing | A network-isolated Pi Bouncer, Bartender and Barback parsed scripted streamed tool calls split across chunks through `docker exec -i`. The checks used no real protected action or credential. None of the candidates was exercised as a complete boundary on this machine.

## Next checks

- Rounds starts one shared engine, with `insecureRootCapabilities` off and one egress proxy. The engine version must match the container-use release. Nesting still lets code in a container start normal containers on that engine. Version one does not test whether one task can read another task's data on the shared engine (user decision, 2026-11-18).
- Choose the one allowlist for version one. An allowed domain can still receive data from the container.
- Pin `environment_source` to the task repository. In multi-tenant mode the agent names any host path ([tools.go](https://github.com/dagger/container-use/blob/2e43e625e95216b719ec9338f4034fd3a0be2734/mcpserver/tools.go#L45-L50)), and `--single-tenant` still accepts a path from the request.
- Give the Bartender an exact tool list without `environment_checkpoint`, which pushes an image to any registry that the agent names.
- Check whether secret references in a repository's `.container-use/environment.json` resolve on the host when an environment starts from an agent branch.
- Find an existing isolation or supervision mechanism that contains detached descendants. Verify identity before signaling any process.
- Test a candidate with the actual delegate, a disposable credential, restricted file and network access, and separate host-controlled approval enforcement.
- Verify that an approval binds the requested action, target, and current state, and that interruption requires a new check before execution.
- Verify that a restarted Bouncer reconciles run identity, process state, worktree ownership, and local-only records before resuming.
