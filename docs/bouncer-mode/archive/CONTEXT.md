# Bouncer mode names

Bouncer mode coordinates work across independent repositories through one user-facing Bouncer. See the overview for current behavior and the remaining plan. The bar is separate from the Rounds source repository unless the user chooses otherwise.

Rounds owns its existing session language in [GLOSSARY.md](../../../GLOSSARY.md). A Task Record is not a session: a task can outlive a session or span several sessions. The `Not` column lists rejected and old names; only `archive/` uses them. An old name with a date is the name that a doc used before that date.

## Names

| Name | Means | Not |
|---|---|---|
| **Bouncer mode** | The Rounds mode that coordinates work across repositories. Its repository records and task records stay in a bar, not copies of application code. | Router Workspace (old name, before 2026-11-24) |
| **Bar** | The Git repository that holds the coordination records of Bouncer mode and their configuration. See `GLOSSARY.md` at commit `124fa0f`. Each organization has its own private bar, which holds only that organization's records and task details. Each bar is a workspace for the Bouncer and its Bartenders. | Workspace (old name, before 2026-11-24), Root Repository (old name, before 2026-11-19), Git superproject, monorepo |
| **Bouncer** | The user-facing coordination role, defined in [GLOSSARY.md](../../../GLOSSARY.md). | router agent; Bartender (old name for this role, before 2026-11-17) |
| **Bartender** | The role that carries out one repository task, defined in [GLOSSARY.md](../../../GLOSSARY.md). In the design, a conversation in the Node Host Harness. | repository agent, network server, Server (old name, before 2026-11-17) |
| **Barback** | The role that does bounded work for one Bartender, defined in [GLOSSARY.md](../../../GLOSSARY.md). In the design, a child conversation of its Bartender. | worker, Runner (old name, before 2026-11-17) |
| **Bouncer mode** | The mode of Rounds in which the pill is the Bouncer and a click on it opens the Bouncer Window. | separate Bouncer app |
| **Bouncer Window** | The native window of Rounds in Bouncer mode. It holds the Bouncer conversation, its results and its decisions. Approvals show as inline cards in the conversation, drawn by host code. In Bouncer mode the pill bounces only when the Bouncer waits for the user. | Task View (replaced 2026-11-19), Tasks section, Task Group (no tasks section, so no task groups, 2026-11-19) |
| **Bouncer Session** | The durable conversation in the Node Host that holds the user's messages, model choice and questions. Rounds reopens it when the Bouncer starts. An interrupted reply stops on restart. | Bartender Session (old name, before 2026-11-17) |
| **Host note** | The button in the Bouncer Window header that counts the other sessions that need input or failed, as Rounds sees them. Its popover lists them and opens the session list. The Bouncer does not see these sessions. | Bouncer report |
| **Set Up row** | The sidebar row of the Bouncer Window that shows while no organization has a ready bar, and opens Settings > Organizations. The Bouncer starts only when no step is missing. | Setup row in Your Turn (superseded 2026-11-19) |
| **Fact banner** | A banner from Rounds above the Bouncer conversation that states a fact Rounds could not confirm, such as an agent that may have stopped, with Check Again. Built in sub-step 01c. | Bouncer reply |
| **Node Host** | The one Node process that Rounds starts and stops. It runs the pi-durable Harness that holds the Bartenders and Barbacks. | |
| **Authority Chain** | The order of decision authority: user, Bouncer, Bartender, then Barback. A Barback sends every request for input to its Bartender and never asks the user directly. The Bartender decides within its authority and asks the Bouncer when unsure. If the Bouncer cannot guide the Bartender without user input, it presents up to three options and recommends one. The user's direct instruction takes precedence over agent decisions and bar policy, within applicable platform and external constraints. | |
| **Approval Boundary** | The user's rules for actions that require explicit consent. Agents cannot delegate more authority than the user grants. When the Bouncer cannot determine whether an action needs approval, it prepares the action and asks. | |
| **Approval Request** | A request for the user's consent to one protected action. A Bartender reviews a Barback's request before it reaches the user. The coordination runtime records the parent chain and can send a known approval request to the Bouncer Window after Bartender review without a Bouncer model turn. A Bartender asks the Bouncer first when uncertain. The requesting agent waits for the answer; unrelated work can continue. Rounds shows the request as Needs input and uses its configured remote alerts only when the organization permits the information to leave the machine. If permission is unknown, keep the alert local. A pending request survives a restart. Rounds rechecks the revision and remote URL itself; if they changed, it drops the request and asks again for the changed action. The user can approve or reject a request. A rejection stops the requested action, records the reason, and returns it to the requesting agent. | Interrupted approval (dropped 2026-11-19) |
| **Repository Task** | A task assigned to one Bartender for work in one repository and an assigned checkout or worktree. Several repository tasks can target the same repository on separate worktrees. A repository task can be part of a cross-repository task. | |
| **Task Record** | The durable record of a task's scope, state, relationships, and results. Bouncer mode keeps the Task Records of an organization in that organization's bar, commits them locally and pushes them only when the user asks, and only to the organization's owner. If unrelated changes exist, it asks before committing. | |
| **Git Checkpoint** | A Git-backed snapshot used for local recovery. It is separate from the branch history that holds Task Records. Its retention and restore behavior must protect durable records and unrelated work. Whether the container-use clone replaces it is open ([slice 03](slices/03-dispatch-and-results.md)). | |
| **Decision Record** | A durable record of a task decision, including the decision, its reason, the responsible user or agent, its time, and its task. Records include routine agent decisions and approval outcomes. The log records decisions rather than private model reasoning. Its scope is open ([slice 03](slices/03-dispatch-and-results.md)). | |
| **Organization Boundary** | A user-defined boundary that governs which organization context a task can load and where its information can be stored or sent. Apply these boundaries to Rounds alerts and ticket lookups for every session, including sessions outside Bouncer mode. Match registered repositories to organizations using directory or Git remote rules defined by the user. Keep alerts and ticket lookups local for unmatched or conflicting matches until the user classifies them. Remote transmission also requires permission under the applicable organization rules. | |
