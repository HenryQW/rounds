# Decisions

Owner decisions for Bouncer mode, newest last. Entries of the same day are in the order of the docs that recorded them. Earlier owner choices with no recorded date are in the [agreed scope](archive/overview.md#agreed-scope). Defaults that an agent took are in the slice briefs under `Decided`, marked *default*.

- **(Superseded by "One bar for each organization", 2026-11-24.)** **Root repository visibility (owner, 2026-11-16):** Use one root Git repository for Bouncer mode; it can be public or private. A public remote, or a remote whose visibility cannot be verified, needs the user's acknowledgement before use, and each push still needs approval. When the root cannot hold an organization's task details, keep them in an approved local folder and put only permitted metadata in Git. One repository keeps one central view of tasks; visibility does not grant permission to store an organization's information. Full record: [decisions/repository-visibility.md](archive/decisions/repository-visibility.md).
- **Authority and approval enforcement (owner, 2026-11-17):** Authority runs from the user to the Bouncer, the Bartender, then the Barback. A Barback asks its Bartender, never the user. A required approval stays the user's decision, and version one protects it with isolation and guarded execution bound to the exact action and target. Agents with a shell and inherited credentials can bypass a prompt-based approval. Full record: [decisions/authority.md](archive/decisions/authority.md).
- **(Superseded by "Bouncer mode in Rounds", 2026-11-19.)** **Bouncer conversation in a Pi terminal (owner, 2026-11-17):** The user talks to the Bouncer in a Pi terminal session.
- **(Superseded by "Bouncer mode in Rounds", 2026-11-19.)** **Keep the pill (owner, 2026-11-18):** Keep the pill and its layout. It counts all of Your Turn, task rows included.
- **(Partly superseded by "One bar for each organization", 2026-11-24: the task detail folders.)** **Bar setup for version one (owner, 2026-11-18):** Rounds does not ask a Git host for remote visibility, because the query sends the remote address off the machine; every remote needs the may-be-public acknowledgement for its exact set of URLs. Rounds can create the repository on request, writes only `rounds-bar.json`, and adds no remote, commit or push. Machine-specific choices and one approved private task detail folder for each organization stay in local settings. The rule is in specification section 2.7.2 at commit `124fa0f`. See the [archived overview](archive/overview.md#built-so-far).
- **(Partly superseded by "One ework container for each organization", 2026-11-25: the per-task container for ework workers.)** **Option 3: container-use for all agent work (owner, 2026-11-18):** Agents see container-use tools only, on one shared Dagger engine with `insecureRootCapabilities` off and one egress proxy. Agents produce and Rounds publishes; a Bartender that needs input ends as Blocked; container-use supplies the disposable clone and the result branch `container-use/<env>`; Rounds owns the lifetime of the agents. Version one does not test data isolation between tasks on the shared engine. A container-use code path gave a full root escape into the engine, and the engine setting closes it ([evidence](archive/feasibility-check.md)). Design: [bouncer review, option 3](archive/bouncer-review.md#option-3-pi-on-the-host-container-use-for-all-work).
- **pi-durable Harness for Bartenders and Barbacks (owner, 2026-11-19):** Bartenders and Barbacks run in a pi-durable Harness, not through `acp_delegate` or Pi RPC. A Barback is a child conversation of its Bartender, so the delegate tool is a pi-durable subagent tool. Approval requests are `beforeTool` gates that park the call until the user answers. pi-durable gives recovery, parked approvals and child abort ([probe](archive/reuse-review.md#pi-durable-checked-2026-11-18)).
- **(Superseded by "Build on unreleased pi-durable", 2026-11-19.)** **Wait for a pi-durable release (owner, 2026-11-19):** Wait for a pi-durable npm release with signals before you build the approval gate. Do not pin a source build. Build the other slices on npm 1.5.2.
- **(Partly superseded by "Bouncer mode in Rounds", 2026-11-19: Surface, Board, Choice, Result, Decision log and Agent chart; by "Set Up row in the Bouncer Window", 2026-11-19: Setup.)** **Attention review (owner, 2026-11-19):** Approve Surface, Board, Approval, Choice, Result, Decision log, Agent chart, Backup note, Root records and Setup as proposed in the [attention review](archive/attention-review.md). Approval groups the exact push and draft pull request actions of one result. The backup note shows once, in Settings > Bar and on the setup row. Task Records commit locally and push only when the user asks.
- **Restart rechecks replace the Interrupted state (owner, 2026-11-19):** Supersedes the Interrupted approval and Recovery rows of "Attention review". A pi-durable gate keeps a request parked across restarts. Rounds rechecks the revision, remote URL, agents and checkouts itself; if the action changed, it drops the request and asks again.
- **(Partly superseded by "Approvals as inline cards", 2026-11-19: the native dialog form; by "Bouncer on pi-durable", 2026-11-20: `pi --mode rpc` in version one.)** **Bouncer mode in Rounds (owner, 2026-11-19):** Supersedes "Bouncer conversation in a Pi terminal" and "Keep the pill", and the Surface, Board, Choice, Result, Decision log and Agent chart rows of "Attention review". The Bouncer interface is a Bouncer mode of Rounds, not a separate app. In Bouncer mode the pill is the Bouncer: it stays still while nothing waits and bounces only when the Bouncer asks for an approval or an answer; a click opens the Bouncer Window. The window holds the conversation and shows approvals as native dialogs from host code, never as model text. The session window has no Tasks section; the decision log stays in task records. Version one drives Pi with `pi --mode rpc`; the Bouncer moves to pi-durable later, so the window talks to the Bouncer through one adapter. Brief: [slice 01](archive/slices/01-bouncer-mode.md).
- **Build on unreleased pi-durable (owner, 2026-11-19):** Supersedes "Wait for a pi-durable release". Build pi-durable from source at one pinned pi commit, `5a14e69c067d40dfbff4f2fff7d3b34c897e2dc9`, and move the pin on purpose. That commit has signals and gates, and upstream CI passed. The approval gate and publication follow slice 3. Brief: [slice 02](archive/slices/02-node-harness-host.md).
- **Bouncer Window has a task sidebar (owner, 2026-11-19: "i think C task sidebar makes more sense, Easier for human readability, and if we're going to do a chat UI, we need to learn from Cloud Desktop."):** The Bouncer Window uses mockup C: a sidebar of tasks, and the conversation of the whole Bouncer thread or of one selected task. Mockups A (single column) and B (inspector) are rejected. The chat follows the patterns of the Claude desktop app Code tab where they do not conflict with an earlier decision. The reason: a task list is easier for a person to read, and users already know that chat layout.
- **Approvals as inline cards (owner, 2026-11-19: "use inline"):** Supersedes the native dialog form in "Bouncer mode in Rounds". Rounds host code draws each approval request as a card in the Bouncer conversation, under the result it approves, as the Claude desktop app shows permission cards. The card uses the window material, a lock and "From Rounds, not the agent", so it never looks like model text. It lists each exact action, needs a reason to reject, and has no "Always allow". The reason: the user reads the result and its checks while deciding.
- **No shared theme in version one (owner, 2026-11-19: "approve 1 2"):** The Bouncer Window uses native controls and the existing Rounds state colours. The shared theme draft is not applied. The reason: the draft is a local file that the app does not ship, and the state colours keep their meaning.
- **Set Up row in the Bouncer Window (owner, 2026-11-19: "approve 1 2"):** Supersedes the Setup row of "Attention review". When a task needs a missing approval or setup step, a Set Up row shows at the top of the Bouncer Window sidebar, above the tasks, not in Your Turn. The reason: the session window has no Tasks section in Bouncer mode.
- **Bouncer on pi-durable (owner, 2026-11-20: "also we should use pi-durable"):** Supersedes `pi --mode rpc` in version one from "Bouncer mode in Rounds". The Bouncer is a conversation in the Node Host's pi-durable Harness, as the Bartenders are, and it starts with no tools. The Bouncer Window talks to the Node Host through a protocol that Rounds owns, because pi-durable is a library with no RPC mode (checked at pi commit `5a14e69`). The reason: one agent runtime, and the Bouncer conversation and its parked questions survive a restart. Slice 02 adds the durable adapter and removes `PiRPCBouncer` in the same change, with no fallback. `bouncer-mode` does not merge to `main` while the Bouncer runs on `pi --mode rpc`.
- **Workspace renamed to Bar (owner, 2026-11-24):** The Git repository that holds the coordination records of Bouncer mode is a bar. Each bar is a workspace for the Bouncer and its Bartenders. The old name "Router Workspace" for the whole system becomes "Bouncer mode". Code, settings, file names and docs use the new names: `bar-settings.json` and `rounds-bar.json`. The feature is not released, so Rounds reads no file with the old name.
- **One bar for each organization (owner, 2026-11-24: "2, and do a check that a repo can be only pushed to its own organization, e.g, HenryQW/Rounds only to HenryQW, Evermark/hub only to Evermark. which means each bar can only serve one organization"):** Supersedes "Root repository visibility" and the task detail folders of "Bar setup for version one". Each organization has its own bar, a private Git repository that holds all of that organization's task records and details; there are no separate detail folders. A bar never holds another organization's records. Rounds pushes a repository, a bar included, only to a remote whose owner belongs to the repository's organization: `HenryQW/Rounds` only to `HenryQW`, `Evermark/hub` only to `Evermark`. A project with no organization has no bar and cannot push. The reason: one storage rule instead of two, and a push cannot move one organization's work or records to another. The Bouncer still shows the tasks of all bars in one view.
- **One owner for each organization (owner, 2026-11-24: "1. Owner list in Orgs", then "HenryQW is not an org, it is a personal account, so no multiple owners"):** Settings > Organizations records one remote owner for each organization: a host and an account, such as `github.com/HenryQW` (a personal account) or `github.com/Evermark`. The account can be a person or a GitHub organization. Rounds refuses a push to any other owner, a fork included. An organization with no owner cannot push.
- **Dispatch, task creation and conversation replay (owner, 2026-11-24).** Reserve one writer per checkout. A task waiting for approval allows work in another checkout. Keep the restart checks before resuming work. Publish the assignment before adding a task to its organization's graph. Read conversation history once on a clean open and refresh it after recovery changes it. [Dispatch and task storage](archive/slices/03-dispatch-and-results.md) and [Bouncer Window brief](archive/slices/01-bouncer-mode.md).
- **Enroll each checkout once for its organization (owner, 2026-11-24).** Keep the enrollment across tasks. Each task rechecks its checkout, instructions and permissions before starting. [Task dispatch](archive/slices/03-dispatch-and-results.md#local-runtime).
- **Defer organization data rules for the Desktop experiment (owner, 2026-11-24).** Leave the organization data rules for a future implementation while exploring Claude Desktop coordination. This does not remove existing controls or approve a production data store.
- **Simplify session safety for Claude Code (owner, 2026-11-25).** For this version, drop the safe session design and rely on repository organization and owner. The effect on the earlier isolation, approval and concurrent-writer decisions needs clarification before implementation.
- **Explore orchestration in Claude Desktop (owner, 2026-11-25).** Investigate using Claude Desktop skills to coordinate its Code sessions instead of a native macOS orchestrator. A concurrent CLI and Desktop probe created separate conversation branches. Validate Desktop session creation, workspace selection and messaging before revising the implementation plan.
- **GitHub Issues as the version one tracker (owner, 2026-11-25).** Use GitHub Issues as the work tracker for Bouncer mode in version one. Do not use Linear as a Bouncer work tracker in this version. This decision does not select an execution backend or change the existing bar storage design.
- **One ework container for each organization (owner, 2026-11-25: "One container per organization").** If ework runs Bouncer workers, all workers of one organization run in one ework container, and that container is the isolation boundary. Each organization gets its own container and data. This replaces the per-task container of "Option 3" for ework workers only. This decision does not select ework as the backend.
- **Report the ework gaps upstream (owner, 2026-11-25: "2").** Report the gaps that the [ework integration tests](archive/research/ework-integration-tests.md) found to the ework project, as issues. Do not fork ework now. ework stays a candidate backend until the gaps are fixed. Each issue or comment is a public message and needs the owner's approval before it is sent.
- **(Partly superseded by "Bouncer plugin in Rounds", 2026-11-26: the `henry` skill as the home of the Claude desktop Bouncer.)** **Bouncer mode runs as the Claude Desktop skill (owner, 2026-11-25: "we implemented claude desktop bouncer mode as a skill ... without separate task management, that is handled by claude desktop").** Bouncer mode runs as the `henry` skill (`bouncer.md`) in Claude desktop. Claude desktop holds the sessions and the task state, and the session titles hold the pool state. Rounds keeps no task records for this form. It reads only the titles: a Bartender is a subagent of its Bouncer, and `!<n> Bouncer` is a question (spec 2.1, commit `124fa0f` on `feat/desktop-bouncer-sessions`). This decision does not remove the Rounds-hosted design in this folder. Its future is open.

- **Archive the Rounds-hosted design (owner, 2026-11-25: "1.").** Archive the Node Host, Harness, containers, bars, task records, approval cards and slices 01 to 04. Remove the Rounds-hosted code. The `henry` skill in Claude desktop runs Bouncer mode. Rounds reads only the session titles.
- **Bouncer plugin in Rounds (owner, 2026-11-26: "Rounds, second runtime").** This repository ships the Claude desktop Bouncer runtime as a Claude Code plugin, `bouncer` in [`plugins/bouncer`](../../plugins/bouncer/README.md), which a user installs with `/plugin`. The plugin has no private content: the status codes and the approval rules come from the user's plugin configuration and own rules. The `henry` skill can keep its own copy. This decision does not restore the archived Rounds-hosted design.
- **Bouncer state in the plugin data folder (owner, 2026-11-26: "agree with the change, go ahead and build it").** The `bouncer` plugin keeps its queue and its default ticket records in the data folder that Claude Code gives the plugin (`CLAUDE_PLUGIN_DATA`, `~/.claude/plugins/data/bouncer-rounds/`), not in the Bouncer's working folder and not in a hand-made `~/.claude/bouncer/`. The pool stays in the session titles. A user's own rules may name another place for ticket records.
- **The advisor settles every question first (owner, 2026-11-26: "can we merge them?").** In the `bouncer` plugin, a Bartender and the Bouncer consult the advisor (if the setup has one) for any question that rules and defaults do not settle, technical, product or priority, before it reaches the user. An action that the user's rules say needs approval goes to the user directly, with no advisor call. A Mechanical Bartender never consults the advisor. This moves the owner's own overlay rules into the plugin, so `/bouncer:bouncer` alone is the whole Bouncer.
